个人主页技术栈：两套方案与选择依据

日期：2026-09-25。状态：选型前方案对比，保留为历史参考。本报告沿用调研时已核查的官方文档与参考源码；对比阶段的联网复查连接失败。成本比较属于针对项目需求的工程判断，未进行原型、性能或设备实测。

**项目所有者已确认采用 Astro + TypeScript + xterm.js，见 [技术选型决策](../../docs/decisions/0001-tech-stack.md)。** 下文记录候选方案的取舍，不再表示当前选型尚未确定；后续设计与实现以已确认决策为准。

**Astro + TypeScript 和 Vite + 原生 TypeScript 都可以满足当前要求。** 两者可以具有相同的终端外观、命令输入和内容导航。选择主要取决于内容增长方式、页面复用需求，以及愿意维护多少构建逻辑。

前面的讨论也涉及 xterm.js。它属于终端呈现层，与 Astro/Vite 的工程组织选择相互独立。下面先比较两套工程方案，再比较终端呈现方式。

| 比较项 | 方案 A：Astro + TypeScript | 方案 B：Vite + 原生 TypeScript |
| --- | --- | --- |
| 页面组织 | Astro 页面、布局和组件 | HTML 入口、CSS 和 TS 模块 |
| 核心内容 | Markdown/JSON 在构建时生成 HTML | 首版直接写在 HTML；数据驱动的静态生成需自行补充 |
| 终端交互 | 浏览器端 TS 操作 DOM | 浏览器端 TS 操作 DOM |
| 学习成本 | 学习 Astro 模板、内容集合和构建环境边界 | 主要是 HTML、CSS、TS 与 Vite 配置 |
| 首版依赖 | Astro 及其构建工具链 | Vite、TypeScript；基础方案依赖面较小 |
| 样式 | 原生 CSS、组件局部样式和全局变量 | 原生 CSS、CSS Modules 或命名约定 |
| 内容维护 | Markdown 与字段校验已有配套能力 | 简单页面直接改 HTML；Markdown 工作流需选插件或写脚本 |
| 多页扩展 | 页面、布局和内容集合可组织详情页 | Vite 支持多页入口；公共模板与批量内容页需自行组织 |
| SEO 与禁用脚本访问 | 按方案生成完整内容 HTML | 按方案直接提供完整内容 HTML，同样可以满足 |
| 加载性能 | 可只发送交互脚本，不必引入 UI 框架运行时 | 同样可只发送少量脚本；实际体积需要测量 |
| 类型检查 | astro check | tsc --noEmit；Vite 的 TS 转译不代替类型检查 |
| GitHub Pages | 构建后发布静态文件 | 构建后发布静态文件 |

Astro 提供内容集合、脚本处理和按需交互机制；Vite 主要负责开发服务器与生产构建，也支持 HTML 入口、TypeScript 和静态部署。基础 Vite 项目需要另外组织内容生成流程。[Astro 内容集合](https://docs.astro.build/en/guides/content-collections/)、[Astro 脚本处理](https://docs.astro.build/en/guides/client-side-scripts/)、[Vite 功能说明](https://vite.dev/guide/features.html)、[Vite 静态部署](https://vite.dev/guide/static-deploy.html)。

**方案 A 的具体建议是 Astro + TypeScript + 原生 CSS + Markdown/JSON。** 使用静态输出，不依赖请求时服务端能力。Astro 组件负责 HTML，独立 TS 模块负责命令和输入逻辑；当前无需 React。

它的主要优点：

- 内容与页面结构分开维护。新增项目时可以增加 Markdown 文件，模板统一生成列表和需要的详情页。
- 公共布局和组件减少重复标记，内容集合可校验字段，适合论文和项目持续更新。
- 核心内容在构建时生成到 HTML，交互可以独立增强；今后有复杂组件时也可按需接入 UI 框架。

它的主要缺点：

- 需要学习 Astro 模板、文件约定，以及构建时与浏览器代码的边界。
- 增加框架和集成的升级维护；若长期只有少数固定栏目，部分能力可能用不上。
- 命令历史、补全、焦点、手机输入等仍需自行实现与验证，框架不会自动解决终端交互设计。
- 如果整个站点逐渐变成高度动态的终端应用，静态内容生成带来的收益会相对缩小。

例如，新论文既要出现在首页精选区，又要出现在论文列表，未来还要有独立介绍页时，集中维护一份内容并由不同模板使用，更能体现 A 的价值。[Astro 内容集合](https://docs.astro.build/en/guides/content-collections/)、[Astro 渲染模型](https://docs.astro.build/en/concepts/islands/)。

**方案 B 的具体建议是 Vite + TypeScript + HTML/CSS。** 首版保持一个静态 HTML 主页，核心信息直接写在 HTML 中，TS 负责交互。命令注册、历史记录和导航分成可复用模块。

它的主要优点：

- 概念和约定较少，熟悉基础前端即可直接修改页面、样式和事件处理。
- 固定单页的初始结构简单，不需要先设计内容集合与模板体系。
- DOM 与交互完全由项目控制，适合小范围交互实验。
- Vite 已提供开发服务器、TS 转译和生产打包，基础构建不需要从零实现。

它的主要缺点：

- 重复的项目和论文条目需要手工保持结构一致，列表增长后容易增加维护工作。
- Markdown、字段校验、公共模板、批量详情页等能力需要另外组织。
- 手工实现内容流水线后，需要维护项目自己的约定和代码；最初省下的学习成本可能转变为后续维护成本。
- 若改为从 JSON 在浏览器中生成所有内容，无脚本访问和初始 HTML 内容就需重新处理；保持静态 HTML 或增加构建时生成都能解决。

例如，只有一个主页、偶尔新增一条论文时，直接修改一小段 HTML 完全合理。如果希望一次填写数据就更新多个页面，A 的现成功能通常更省长期维护工作。这里没有固定的条目数量门槛。[Vite 功能说明](https://vite.dev/guide/features.html)。

**两套方案的性能不能仅凭框架名称排序。** Astro 构建工具较多，不等于访客必须下载更多 JavaScript；原生 Vite 项目也可能因客户端渲染和附加依赖变大。应在相同内容、相同交互范围下比较实际产物。两套方案都可以保持直接可读的 HTML 和少量客户端脚本。

**xterm.js 的取舍是另一项决定。** Astro 和 Vite 都可以使用原生 DOM，也都能加载 xterm.js。参考主页采用 Vite + TypeScript + xterm.js，并额外实现内容转换与 Shell/TUI 层。[参考依赖](https://github.com/jiangyy/jiangyy.github.io/blob/main/package.json)、[参考架构](https://github.com/jiangyy/jiangyy.github.io)。

| 比较项 | 原生 HTML/CSS + TS | xterm.js + TS 命令与内容适配 |
| --- | --- | --- |
| 主要优点 | 内容排版、语义结构和普通网页访问容易沿用 | 终端控制序列、光标和屏幕输出行为有现成基础 |
| 终端体验 | 可做提示符、回显、历史和补全；复杂屏幕行为需自定义 | 更适合高度拟真的终端显示和 TUI 探索 |
| 学术内容 | 标题、摘要、图片和链接直接使用 HTML | 需要设计终端输出转换，或与普通 HTML 内容协作 |
| 浏览器习惯 | 链接、页面滚动和文本选择有原生基础 | 需结合终端行为验证焦点、滚动、选择、历史和手机输入 |
| 开发代价 | 简单命令较低；追求完整终端行为时手写工作增加 | 省去部分终端显示实现，但增加内容适配与集成工作 |
| 无 JavaScript 时 | 核心 HTML 可直接阅读 | 终端依赖脚本，需要另外生成可读的静态内容 |
| 适合的目标 | 可直接浏览且提供命令交互的主页 | 把终端操作与屏幕行为作为主要体验的主页 |

xterm.js 是终端组件，不自动提供网站内容系统，也不要求连接真实 Shell。可以只处理预定义前端命令。不能因此断言它没有链接、选择或可访问性支持；这些方面应检查具体集成。[xterm.js 官方介绍](https://xtermjs.org/)。

选择 xterm.js 时，建议用同一份内容生成终端数据与静态 HTML，避免手工维护两份资料。首屏主动呈现介绍，普通访客有可点击的内容入口；禁用脚本、手机输入和深链接都列入验收。管道、分页和路径操作只在明确需要时增加。

**可以按以下偏好选择组合。**

| 你的优先级 | 建议组合 | 主要代价 |
| --- | --- | --- |
| 持续维护论文和项目，可能增加详情页或文章 | A：Astro + TS + 原生 DOM | 学习和维护 Astro 约定 |
| 固定的小型单页，希望主要使用基础前端知识 | B：Vite + TS + 原生 DOM | 内容增长后自行补模板与生成流程 |
| 最看重参考主页那样的终端操作体验 | B 的终端变体：Vite + TS + xterm.js | 维护内容适配并专门验证普通网页访问体验 |

选型前，A 是默认推荐，B 是可行的简化方案。最终确认的组合是 Astro + TypeScript + xterm.js，由 Astro 组织内容和生成静态站点，xterm.js 提供终端呈现；具体交互范围与内容协作方式将在 Spec 和 Design 中明确。

为了控制未来迁移成本，两套方案都应将命令解析、历史和导航定义放在独立 TS 模块中。Vite → Astro 主要涉及模板、内容集合和构建；DOM → xterm.js 主要涉及渲染、输入与内容转换。迁移不是零成本，但这两项选择也不必绑定。

两套方案都建议提交 npm 锁文件、独立运行类型检查、覆盖关键交互与桌面/手机布局，并通过 GitHub Actions 部署到 GitHub Pages。技术选型现已确认；创建应用不属于本次文档记录的范围。[Astro 部署说明](https://docs.astro.build/en/guides/deploy/github/)、[Vite 部署说明](https://vite.dev/guide/static-deploy.html)。

背景依据、命令范围与验收建议见 [前期调研报告](./tech-stack-research.md)。
